## Description

Add the configuration that names stores, before anything serves them.

A store list comes from three places. A repeatable `--store` flag beats the
`GIT_TICKET_CANVAS_STORES` environment variable, which beats a `--config` file.
The file is the durable form, the environment variable suits a container, and
the flag suits one session.

`gopkg.in/yaml.v3` is already a direct dependency, so the file needs no new one.

A relative path inside the configuration file resolves against that file's own
directory rather than the working directory, so a checked-in configuration is
portable. `~` expands.

Store names are restricted to the character set `validBoardName` already
enforces for boards, because a name appears in a URL.

This ticket adds types, parsing, merging, and validation. It changes nothing
about serving, so it lands with unit tests and no behavior change.

## Acceptance criteria

- [x] A YAML file, an environment variable, and a repeatable flag each produce a store list.
- [x] Precedence is flag over environment over file, and a test covers each pair.
- [x] A relative path in the file resolves against the file's directory, and ~ expands.
- [x] An invalid store name, a duplicate name, and a duplicate path are rejected with a message naming the offender.

## Implementation plan

Add `internal/config` holding types, the three sources, merging, and
validation. Nothing opens a store here. Producing a validated list is this
ticket; opening one is the registry's work in TKT-01M2HPB9Z (Route the API by
store key behind a store registry).

### Types

`Store` is one configured store: `Name`, `Path`, `Actor`, `ReadOnly`. `Root` is
a directory to walk: `Path`, `Depth`, `Exclude`. `Config` holds `Roots`,
`Stores`, and a top-level `Exclude`. `Root` and `Exclude` are parsed and
validated here but consumed by the walk in TKT-01M2HPBA3 (Walk a root for
ticket stores with a bounded depth), so this ticket lands them as fields and
leaves them unused.

### The --store flag keeps its current meaning

Today `--store` is a single directory to discover a store from, and
`git-ticket-canvas --store .` has to keep working unchanged. So the flag
becomes repeatable and accepts two forms: `PATH`, which derives a name from the
directory's base name, and `NAME=PATH`, which sets one. Splitting on the first
`=` only keeps `name=C:\path` parsing correctly on Windows.

Path resolution here means expanding `~`, making the path absolute, and
cleaning it. Whether a path is opened directly or discovered by walking up from
it stays with the registry, because `ticket.Discover` walking up is what makes
`--store .` work from a subdirectory and that behavior must not move.

### Precedence over a list

`GIT_TICKET_CANVAS_STORES` holds `NAME=PATH` entries joined by
`os.PathListSeparator`, which is `:` on Linux and `;` on Windows, so a Windows
drive letter does not collide with the separator.

Precedence is by name, not whole-list replacement. A `--store` flag naming a
store that the file also names replaces that one entry and leaves the rest of
the file alone. Replacing the entire list would mean you cannot add one store
for one session without restating your configuration, which is the common case.

A relative path inside the configuration file resolves against that file's own
directory. A relative path from a flag or the environment resolves against the
working directory. The file is a document that can be moved or checked in; a
flag is typed in a shell that already has a working directory.

### Validation

A name is letters, digits, `-`, and `_`, at most 64 characters, which is what
`validBoardName` in `internal/api/snapshot.go` already enforces for boards. A
name appears in a URL, so the two have to agree. The character set is
duplicated rather than shared for now: exporting it from `internal/api` would
make `internal/config` depend on the package that will depend on it.

Two stores with the same name is an error. Two names for the same resolved path
is also an error, because the id is what appears in a URL and nothing would say
which of the two a request meant.

Report every validation failure with the offending value in the message, and
report which source it came from. A message that says a name is invalid without
saying which name, in which of three places, costs the reader the search.

### Tests

Table tests over each source, each precedence pair, `~` expansion, relative
resolution from both bases, the `NAME=PATH` and bare `PATH` flag forms, and
each validation failure. No filesystem is needed beyond `t.TempDir` for the
file cases, and no store is opened.

The flags land with the registry.

So read the first acceptance criterion at the level this ticket works at:

### Decisions worth not relitigating

Precedence is per name, not whole-list replacement. A `--store` flag naming a
store the file also names replaces that entry and leaves the rest alone.
Replacing the whole list would mean you cannot add one store for one session
without restating your configuration, and adding one store for one session is
the common case. `TestPrecedenceByName` asserts the other stores survive.

`NAME=PATH` and bare `PATH` are told apart by whether the text before the first
`=` is a name this package would accept. That keeps `--store .` working, keeps
`name=C:\path` parsing on Windows, and stops `/srv/odd=dir` from being read as
a store named `/srv/odd`.

The environment variable joins entries with `os.PathListSeparator`, which is
`:` on Linux and `;` on Windows, so a Windows drive letter does not collide
with the separator.

The name character set is copied from `validBoardName` in
`internal/api/snapshot.go` rather than shared. Exporting it from `internal/api`
would make `internal/config` depend on the package that will depend on it. The
two have to agree because both appear in a URL path, so the duplication is
recorded in a comment on `ValidName` at both ends.

`KnownFields(true)` rejects a key the package does not know, so `store:`
written for `stores:` fails at startup instead of quietly serving nothing.
