## Description

Add `layout` to `DisplayChoices` in `web/src/platform/canvas/viewport.ts`, as a fourth setting chosen by `chooseDisplay` and overridable in the Display panel:

- `phone` when the short side of the window is under 600 CSS pixels, so a phone held landscape is still a phone
- `tablet` when the pointer is coarse and it is not a phone
- `desk` otherwise

The override is stored with the other display overrides. On its own this ticket changes nothing visible except the Display panel. Later tickets read `layout` to decide what to offer.

See `docs/mobile-design-v1.md`, "Choosing the layout".

## Acceptance criteria

- [ ] chooseDisplay returns a layout, with the rules tested as a table including a landscape phone and a narrow desk window
- [ ] The Display panel shows the chosen layout and lets it be overridden, stored like the other overrides
- [ ] The layout is exposed to CSS (for example as a data attribute on html) so stylesheets can key on it
- [ ] Nothing else changes on any layout
- [ ] A stored layout override survives a reload, and an unrecognised stored value is dropped

## Implementation plan

Read before writing: `DisplayChoices` in `web/src/platform/canvas/viewport.ts` holds three fields and `chooseDisplay` fills them from `{width, height, coarse}`. `useDisplay` layers the stored overrides over it with `applyOverrides`, so a fourth field there is picked up by the hook, the reset, and the override count without changes. `recall()` in `web/src/ui/displayPreferences.ts` rebuilds the record key by key from allowlists, so a key without one is dropped on reload. `DisplayDialog` renders one row per entry in the typed `CHOICES` tuple. `App.tsx` writes `targets`, `inspector` and `toolbar` onto `document.documentElement.dataset`.

### Changes

- `viewport.ts`: `export type Layout = 'phone' | 'tablet' | 'desk'`, a `LAYOUTS` constant, a `PHONE_BELOW = 600` threshold on `Math.min(width, height)`, and `layout` in `DisplayChoices`. Order of the rule: phone first (short side under 600, whatever the pointer), then tablet (coarse pointer), then desk. Comment says why the short side: a phone turned landscape is 844x390, whose width would call it a desk.
- `viewport.test.ts`: add `layout` to every existing table row, and a second table for layout alone with a phone in both orientations, a narrow desk window, the 599/600 boundary, a tablet in both orientations, and a touch-screen monitor.
- `displayPreferences.ts`: take the allowlist from `LAYOUTS` and recall `layout`. Test that a stored layout comes back and that an unrecognised one is dropped.
- `DisplayDialog.tsx`: a fourth `Choice<'layout'>`, titled `Layout`, with labels Phone, Tablet, Desk. Placed first, because it is the choice the others sit under once later tickets read it. Dialog tests: the automatic label on a phone, a landscape phone and a desk; an override written and read back through a remount.
- `App.tsx`: `root.dataset.layout` beside the other three, and in the dependency list. No stylesheet reads it yet, so nothing else changes.
- Rebuild `web/dist`.

### Rejected

- Deriving layout from `targets` and `density` instead of storing a fourth setting. The design makes it separately overridable (a phone somebody wants to edit on sets `tablet`), and a derived value cannot be overridden without overriding what it came from.
- Width alone for phone. A landscape phone is 844 wide, over the compact threshold, and would be called a desk.
- Area or diagonal. Neither is more observable than the sides, and the short side is what decides whether a second column fits.
- Putting the layout row after the existing three. It reads as the broadest choice, so first; the order is cosmetic and any browser test that enumerates rows would show it. None exists (searched `tests/browser` for the dialog ids).
