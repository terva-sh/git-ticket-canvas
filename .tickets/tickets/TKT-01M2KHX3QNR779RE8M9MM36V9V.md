## Description

The README argues for a spatial interface over eleven screens of prose and never
shows one. It opens with "an infinite canvas over a git-ticket store" and then
asks the reader to take the canvas on trust. For a tool whose entire claim is
that position carries meaning, a picture is not decoration; it is the argument.

A screenshot pasted in by hand would be worse than none, because it would be
right once. The canvas changes: this session alone added a store picker, a store
browser, display names, and a fix to how the picker closes. An image captured by
hand in September is a claim about the product that nothing re-checks, and the
first person it misleads is the one deciding whether to try it.

So the images have to be generated by a script that can be re-run, against a
committed fixture, with anything that varies per machine or per build held
constant. `scripts/capture-canvas-baseline.mjs` already does this for the review
baseline and is the model to follow rather than duplicate: it unpacks the
committed AHPSH archive, builds and starts the real binary, stubs the version
and store path so the toolbar does not change on every commit, and screenshots
with animations disabled after measuring that six identical runs otherwise
produced three different images.

Target 1920x1080, a 16:9 frame that matches a full screen and renders at a
sensible width in both GitHub's README column and the internal forge's.

One constraint is already documented and must be respected. `docs/canvas-baseline.md`
and the `canvas-visual` recipe record that CI renders text with Alpine Chromium
and font-noto while a developer's machine uses Playwright's Chromium, and that
the two disagree. So these images cannot be byte-compared on CI. Regenerating
them must be easy and recorded; it must not become a gate that fails on a
runner for a reason that is not a defect.

## Acceptance criteria

- [ ] One command regenerates every README image, and running it twice with no code change produces the same bytes.
- [ ] Every image is 1920x1080 at device scale factor 1.
- [ ] The images show the canvas with relationships, a selected ticket's inspector, and the multi-store browser.
- [ ] Nothing per-build or per-machine appears in an image: the version, commit, and store path are held constant, and the capture fails rather than emitting an image if they are not.
- [ ] The README displays the images, and a reader can find the command that regenerates them.
- [ ] No CI job byte-compares these images, because the runner and a developer machine render text differently.
- [ ] The generator takes a tarballed ticket store as its data seed, defaults to the committed example bundle, and captures a named bundle without editing the script.
